Start here

A policy flies. Training teaches it what to avoid.

The policy reads a depth image, its velocity, the goal direction and the clearance margin m, then requests an acceleration. The margin is extra safety distance in metres, set per environment (env.margin). An environment is one of the simulated worlds flown in parallel. Training draws 0.1–0.3 m at random; evaluate.py uses 0.2 m by default (--margin). The simulator applies the request and produces the next drone state.

Training flies this loop for a whole rollout, scores the flight with several losses, and updates the policy's weights. The TOA loss rewards progress along routes around obstacles. The CBF loss penalises approaching an obstacle faster than the remaining clearance allows. Both act only in training: the deployed policy picks each command from its observations.

01How the code fits together

The code has three layers: entry scripts call toanav, which loads DiffPhysDrone. The backend in toanav decides whether DiffPhysDrone runs on its compiled CUDA code or on our PyTorch port.

  • Entry scripts: train.py trains a policy, evaluate.py flies it, and export_onnx.py exports it to ONNX, a portable format for running it outside PyTorch.
  • toanav: this repository's Python package, with TOA, losses, geometry, policy, charpi and backend modules.
  • DiffPhysDrone (pinned at commit 2719361): scenes, depth renderer, point-mass dynamics and neural network.
  • Backend (backend.py): loads DiffPhysDrone. By default it uses quadsim_cuda, DiffPhysDrone's compiled CUDA extension for dynamics, depth rendering and nearest-obstacle queries. Without a GPU or the extension, or with --backend torch, it uses toanav.quadsim_torch, our pure-PyTorch copy (the PyTorch port).

The --dynamics flag picks the plant. --dynamics diffphys uses DiffPhysDrone's point mass. --dynamics charpi calls CharpiDynamics.step in place of env.run. CharpiDynamics is the wrapper class that runs charpi inside the rollout. Observations and losses read the same Env attributes either way. With charpi, the gradient through each step still comes from the point mass, the surrogate.

03Follow one training iteration

An iteration is one training update: new scenes, one rollout, one backward pass, one weight step. train.main runs num_iters of them (50,000 in configs/). Before the loop, make_dynamics(env, args) picks the plant: None (the point mass in env.run) or, with --dynamics charpi, one CharpiDynamics wrapper.

  1. Start new flights

    env.reset() draws 64 scenes, start positions, goals and speeds of 3–13 m/s. It also randomises margins, drag, delays, wind and camera pitch. With charpi, call dyn.reset() afterward (reset order).

    Reset tensors and the charpi config

    Reset fills the scene tensors, env.p and env.p_target (B, 3), and env.margin (B,). The config configs/toa_cbf_charpi.args uses the toa_cbf variant and loss weights and adds --dynamics charpi --charpi_br_fit real --charpi_dr_band narrow.

    Variant
    Named training setup: distance (no TOA or CBF), toa (adds the TOA loss) or toa_cbf (adds the CBF loss as well).
    br_fit
    Measured body-rate response charpi uses: real (flight logs) or sitl (simulation).
    DR band
    Width of charpi's domain randomisation (DR): narrow, real or off. DR draws random physical scales once per episode (one flight), so the policy copes with variation.
    Trim
    A steady state matching the current command env.act. dyn.reset() starts the charpi plant in trim, so it starts without a jolt.

  2. Build the TOA field (TOA variants only)

    With --use_toa, build_toa_field(scene, env.p, env.p_target, …) builds a grid of route lengths to the goal. It stays fixed, without gradients, for the whole rollout. With the default solver it is the slowest step: about 83 % of each iteration, measured on the RTX 5080.

    Field channels and measured build time

    TOAField.volume (B, 5, Nx, Ny, Nz) holds Φ, the three components of ∇Φ, and a validity mask. Its slope ∇Φ is the direction in which route length grows fastest. The mask marks free cells reachable from the goal. Build time is logged as time_toa. Both solvers below are a JFA (jump flooding algorithm). It fills the grid with distances via long, then shorter, jumps, which is fast on a GPU.

    Measured on the RTX 5080 in 300-iteration toa and toa_cbf runs (solver details):

    • Default jfa_safe, which skips jumps through occupied cells (3 passes, 8 cleanup rounds, octile metric): 0.87–0.90 s of a 1.05–1.08 s iteration.
    • Paper-literal JFA (--toa_mode jfa, run as toa_cbf_literal_jfa): 0.09 s of 0.27 s. It follows the paper's Eq. (3)–(4) as printed, so values can leak through thin walls.

  3. Fly the policy for 150 policy steps

    rollout(env, model, args, dyn) flies 150 steps at about 15 Hz (10 s). Each step renders depth, applies the previous command (env.run or dyn.step), then computes the next acceleration u from that depth and the 10-value state. So each command acts one policy step (about 1/15 s) late: one step of command latency.

    Step order, timing and rollout tensor shapes
    • env.render(dt) returns depth (B, 48, 64), without gradients. With dt jitter (training only), each dt is drawn around 1/15 s (standard deviation 10 %).
    • Record p and v_pre (B, 3) and swept sub-positions (M, B, 3).
    • The target is the true goal direction or, with --yaw_drift (on by default), the fixed initial goal vector turned by a per-environment yaw drift. This imitates the slow drift of VIO (visual-inertial odometry: position from camera plus inertial sensor).
    • The wind is an OU process (Ornstein–Uhlenbeck: random, but pulled back toward its mean). Then env.run(ut−1, dt, yaw_ref) applies the previous command. Its yaw_ref, where the nose should turn, is the goal vector or horizontal velocity.
    • With charpi, dyn.step(ut−1, dt, yaw_ref) runs n ticks (10 ms controller-and-plant updates; 6–7 per step, tick count). It updates env.p/v/a/R.
    • preprocess_depth returns (B, 1, 12, 16); build_state returns (B, 10).
    • model(x, state, h) returns the action (B, 3) and GRU state (B, 192). Here h is the GRU state, not clearance. Then action_to_accel turns the action into u (B, 3) by the paper's Eq. (1), u = κ·(R·f − v − g) + g. Here f is the network output and κ a thrust-estimate error factor (details).

    Stacked outputs: p, v_pre, v and target_v (T, B, 3); sub (T, M, B, 3); u (T+2, B, 3). The target velocity target_v that Lv asks for points along the target vector above, with speed min(its length, vmax). Without drift, that length is the goal distance.

  4. Score the flights

    compute_losses(env, roll, args, toa_field) sums weighted penalties: Lv (velocity tracking), Lcollide (collision), Lacc (acceleration) and Ljerk (command smoothness). When enabled, Ltoa adds TOA route progress and Lcbf CBF approach speed. The weights are the paper's Table I (its loss weights), unchanged in configs/: for example, collision 7.0.

    Distance queries and logged metrics

    One scene_sdf call queries all 150 × 10 × 64 = 96,000 sub-positions (T × M × B). It returns the signed distance to the nearest surface (positive outside an obstacle, negative inside) and the outward surface normal n_out; n̂ = −n_out points toward the obstacle. Logging also records success, speeds and clearance.

  5. Update the network and record progress

    total.backward() computes the loss gradient for every policy weight. optim.step() updates the weights; sched.step() advances the learning-rate schedule. Metrics are averaged over 25 iterations and saved to CSV and TensorBoard.

    Gradients through time and the checkpoint

    BPTT (back-propagation through time) runs back through all 150 steps. Each step's dynamics backward multiplies the position and velocity gradients by grad_decay ** dt. With gradient decay λg = 0.4 per second, that is 0.41/15 ≈ 0.94 per 1/15 s step. Over 15 steps (1 s), the decay alone scales those gradients by 0.4. With charpi, the surrogate's backward applies the same decay.

    The checkpoint also saves the camera, yaw and plant settings that evaluation and export reuse (checkpoint config).

04How learning reaches the policy

Only position and velocity carry gradients back to earlier commands, through the dynamics. Every lookup is a constant, and the code attaches a hand-picked gradient to it:

  • the TOA loss uses the field slope ∇Φ;
  • the collision loss uses the outward surface normal;
  • the CBF loss differentiates approach speed with respect to velocity only.

A stop-gradient, sg(·) or detach(), keeps a value but blocks its gradient. In the figure, p̄ = sg(p) is the position with its gradient stopped.

The three hand-picked gradients in code

Each line keeps the lookup's value and supplies the gradient training uses. For TOA: forward, p − p̄ = 0, so the value is Φ; backward, the gradient with respect to p is ∇Φ.

# toa.py, TOAField.straight_through: value from the table, derivative = sampled ∇Φ
phi, grad, valid = self.sample(p)                  # sample() runs under no_grad on p.detach()
return phi + (grad * (p - p.detach())).sum(-1), valid

# geometry.py, differentiable_distance: value sd, derivative = outward normal
return sd.detach() + ((points - points.detach()) * n_out.detach()).sum(-1)

# losses.py, cbf_loss: h and n̂ are constants, only v is differentiated
v_close = (v_hist[:, None] * n_hat_sub.detach()).sum(-1)

The collision loss is evaluated at swept sub-positions p + v·s, with s from 0 to 1/15 s, so its gradient reaches v as well as p.

These are also constant on purpose:

  • the depth image: the CUDA renderer has no backward, so the fallback also runs under torch.no_grad;
  • the attitude update update_state_vec and the target direction;
  • the approach-speed weight inside Lcollide;
  • the airmode term: extra DiffPhysDrone acceleration from fast thrust-direction changes;
  • with --dynamics charpi, the whole controller and plant (next subsection).

Charpi supplies the flight; a simpler model supplies learning

With charpi, the charpi plant supplies the values; the point mass, run alongside as the surrogate, supplies the gradients. The charpi controller and plant run without gradients.

This is a straight-through gradient: one model's values forward, another's gradients backward. In qpg-quad-jax, ctbr_dynamics_pm splits them the same way. CTBR stands for collective thrust and body rates: roll, pitch and yaw rotation speeds, in rad/s. Each policy step has three stages:

  1. Run the surrogate. Call env.run(feasible_accel(u), n·10 ms, yaw_ref) on R_sp, the surrogate's own virtual attitude. R_sp carries the state of the yaw filter (DiffPhysDrone's low-pass filter that turns the heading toward yaw_ref) from step to step. The surrogate gets u clamped by feasible_accel to what charpi can fly level. This run supplies the point-mass gradients and grad_decay, and updates env.p/v/a/act and R_sp. The new horizontal forward axis of R_sp becomes the plant's requested heading.
  2. Run the plant. From the actual state, detached, hold the raw u for n ticks of charpi_tick (controller plus plant).
  3. Combine them. env.p/v/a get the plant values with the surrogate gradients. env.R gets the plant attitude, so rendering and observations see its roll and pitch.
Straight-through merge, and how the surrogate is tuned to the plant 
# charpi.py, CharpiDynamics.step: env.run(feasible_accel(u), ...) has just set env.p/v/a
# (surrogate, with gradient); p, v, acc, q come from n plant ticks under no_grad
env.p = env.p + (p - env.p).detach()        # value = plant, derivative = surrogate
env.v = env.v + (v - env.v).detach()
env.a = env.a + (acc - env.a).detach()
env.R = rotmat_from_quat(q)                 # plant attitude, no gradient

Four choices keep the surrogate close to the plant:

  • Lag. env.pitch_ctl_delay is DiffPhysDrone's acceleration lag rate (s⁻¹, not a delay): about 12 in DiffPhysDrone, SURROGATE_LAG = 5 s⁻¹ here. Per 1/15 s step, the lagged acceleration closes about 28 % of its gap to the command at 5, and 55 % at 12. The value 5 comes from scripts/charpi/fit_charpi_surrogate.py. It flies the charpi closed loop on random 15 Hz commands and fits the first-order lag that best predicts the realised acceleration:
    • real fit: 5.0 s⁻¹, RMS error 1.66 m/s² on RMS |a| = 4.78 m/s² (about 88 % of the variance). Lag 12 gives an RMS error of 2.80 m/s².
    • Other settings: 5.0 with the narrow DR band, 4.0 for the sitl fit, 3.5 with twice as aggressive commands. SITL (software-in-the-loop) is real PX4 code flying a simulated drone in Gazebo (GZ).
    So our drone's acceleration response is about 2.4× slower than the vehicle the paper's simulator assumes.
  • Reset. dyn.reset() sets the lag, scaled by 1 + 0.1·N(0, 1) per episode when randomised. N(0, 1) is a random number from the standard normal distribution (mean 0, spread 1). Reset also sets env.drag_2 to charpi's hover lateral drag: no quadratic term, and a linear term of 4 ωhover ROTOR_DRAG_CONST / mass ≈ 0.24 s⁻¹. Here ωhover is the rotor speed at hover. It sets env.z_drag_coef to 0 (override table).
  • Feasible command. The surrogate gets feasible_accel(u), which also enforces the 60° tilt limit (the largest allowed lean of the thrust axis from vertical). Command components the plant ignores get zero gradient; the plant gets the raw u (limits).
  • Heading state. An earlier version restarted the yaw filter from the plant attitude each step, instead of carrying R_sp. The nose then turned 4–6× slower than DiffPhysDrone asks; test_heading_follows_diffphys_yaw_filter guards this.

05TOA: build the route field

toanav/toa.py builds the TOA field for every scene before each training rollout that uses the TOA loss. That loss reads it to reward progress along routes around obstacles. The default solver, jfa_safe, had 0.2–0.5 % mean error against BFS (mode="bfs"). It left no free cell unreached in the measured comparisons, on DiffPhysDrone training scenes and a layout like the paper's Fig. 3 (viz_toa.py, tests/test_toa.py). Read this module when changing the grid resolution or the route solver.

JFA halves its jump length k (in cells) each round: k = 64, 32, …, 1 on a 128-cell grid. The paper's Eq. (3) as printed checks only a jump's two end cells. So a jump can leak: copy a too-short route length through a wall.

jfa_safe skips any jump that crosses an occupied cell (diagram below). One such pass can leave cells behind obstacles unreached. So it runs the whole schedule three times (--toa_passes 3), then 8 cleanup rounds at k = 1 (--toa_cleanup 8).

Grid size, obstacle marking and the jump update in code

Make a grid around the route

make_grid(start, goal, delta0=0.2, max_voxels=128, pad_xy=3.0, pad_frac=0.1, z_above=4.0)

Axis-aligned box around start and goal, padded sideways by max(3 m, 10 % of the span), up to 4 m above the higher end. Cell size δ = max(0.2, extent / 127) per environment; shape is the batch maximum, capped at 128. The first z-layer sits half a cell above the ground, so the grid edge is the floor. Returns a GridSpec(origin, delta, shape) with centers() and to_index(p).

Mark occupied grid cells

rasterize(scene, grid, inflate=0.2, slack=0.5)

Rasterisation marks which cells obstacles occupy: occupancy (B, Nx, Ny, Nz). A cell is occupied when its centre is within slack·δ of a primitive, so thin obstacles are not missed. Each type gets its cheapest exact test. Vertical cylinders use the (x, y) plane, broadcast over z; horizontal ones use (x, z). Boxes use a batched einsum of three 1-D interval masks; spheres use a loop. Then inflation grows occupied cells by 0.2 m so routes keep some clearance: a dilation by round(inflate/δ) cells.

Spread route lengths through free space

propagate(occ, goal_idx, delta, mode, metric, n_cleanup, n_passes)

Propagation spreads route lengths outward from the goal through free cells. Each JFA round calls relax(G, k, …), keeps min(G, candidate) and resets occupied cells to ∞. jfa_levels gives that schedule of k.

relax covers all 26 jump directions with 1-D passes. mx, my, mz hold the face jumps; passes over them (mxy, …) add edges and corners. Face, edge and corner jumps cost 1, √2 and √3 times k·δ: the octile metric. In jfa_safe mode each leg is checked against a precomputed occupancy window:

def _axis_min(X, k, dim, blocked=None):
    fwd, bwd = _shift(X, k, dim, math.inf), _shift(X, -k, dim, math.inf)
    if blocked is not None:                        # blocked[i]: any occupied voxel in [i, i+k]
        fwd = fwd.masked_fill(blocked, math.inf)
        bwd = bwd.masked_fill(_shift(blocked, -k, dim, True), math.inf)
    return torch.minimum(X, torch.minimum(fwd, bwd))

Only valid samples count in the TOA loss: inside the grid, with all eight surrounding cells reachable and free.

Field channels, lookup and the straight-through value

Assemble the field and its slope

build_toa_field(scene, start, goal, …) → TOAField

Grid, occupancy (3 × 3 × 3 cells around start and goal forced free), propagation. Then three unmasked relax steps extend the field a few cells into obstacles; any remaining ∞ becomes max + δ. Both keep lookups and torch.gradient finite. volume stacks Φ, ∂Φ/∂x, ∂Φ/∂y, ∂Φ/∂z and valid (reachable and free).

Sample the route length and its gradient

TOAField.sample(p) / straight_through(p)

One F.grid_sample call reads all five channels at (…, B, 3) positions by trilinear interpolation: blending the eight surrounding cell values. The volume is laid out (D, H, W) = (x, y, z), so coordinates go in as (z, y, x); without that flip the field is silently transposed.

straight_through returns Φ̃: the table value forward, with ∇Φ as its gradient backward (the paper's Eq. (5)). losses.toa_loss averages Φ̃ over valid samples only.

06Losses: score a flight

toanav/losses.py turns rollout tensors into training penalties. Lower loss means better velocity tracking, route progress, clearance and smoother commands. train.compute_losses picks the enabled terms and weights them.

The CBF loss penalises approach speed above k · h, with CBF gain k = 2.5 s⁻¹ (--cbf_k). So at h = 1.2 m the allowed approach speed is 3 m/s. Only points within the activation distance dact = 1.5 m count (h < d_act, --cbf_dact).

train.compute_losses sets up these distances (sd: signed distance). Check them when changing the terms:

  • d = sd − drone_radius, with gradient through the normal.
  • h = sd − drone_radius − margin for the CBF, with no gradient.
  • d − margin for the collision term, unless --no-collide_use_margin.
  • n̂ = −n_out, toward the obstacle.
Loss signatures, input shapes and the CBF code

In cbf_loss, each active point adds softplus(β·(v_close − k·h)), where v_close is the approach speed v·n̂. Softplus, log(1 + ex), is a smooth max(0, x). β = 2 (--cbf_beta) sets its sharpness: 1 m/s over the limit costs softplus(2) ≈ 2.13.

def cbf_loss(v_hist, h_sub, n_hat_sub, k=2.5, beta=2.0, d_act=1.5):
    h = h_sub.detach()
    v_close = (v_hist[:, None] * n_hat_sub.detach()).sum(-1)       # (T,M,B)
    active = (h < d_act).float()
    s = (F.softplus(beta * (v_close - k * h)) * active).sum()
    n = active.sum()
    return s / n.clamp_min(1.0), active.mean()

07Geometry: measure obstacle clearance

toanav/geometry.py finds the exact signed distance to the nearest obstacle surface and its outward direction. Training uses it for the collision and CBF losses; evaluation uses it to detect collisions.

The ground at z = −1 counts as an obstacle. differentiable_distance then gives the distance a gradient with respect to position, without changing its value.

Distance queries, surface normals and their gradients

Find the nearest surface

scene_sdf(points, scene, ground_z=-1.0) → (sd, n_out)

For points (…, B, 3): signed distance to the nearest surface and its outward unit normal, under no_grad. Each primitive type is checked against all points at once; argmin picks the nearest per type, and types merge in order with the ground plane. Boxes use the standard box SDF; inside a box, the normal is the nearest face's axis.

Supply the distance gradient

differentiable_distance(points, sd, n_out)

Adds n_out·(p − sg(p)): zero in value, but it gives the distance the first-order gradient n_out with respect to position.

Why not DiffPhysDrone's nearest pointquadsim_cuda.find_nearest_pt gets the direction right but not the length. For spheres and cylinders it returns o + dist·(c − o) (o: query point, c: centre). So |nearest − o| is dist·|c − o|, not dist: a sphere of radius 0.5 m centred 2 m away gives 3 m, not 1.5 m. The paper's CBF compares a distance with a speed, so it needs exact values.
The ground is an obstacleBecause scene_sdf includes the ground, the CBF also caps descent speed near it at k·h. Training starts 0.4–1.5 m above the ground. So with dact = 1.5 m, every point on the start–goal lines is active (69 % without the ground). The logged cbf_active is about 0.87 (toa_cbf, iteration 300). The paper does not say whether its obstacle set includes the ground. This is an observation; the code was not changed.

08Policy: turn observations into commands

toanav/policy.py prepares the depth image and state for the network and turns its output into an acceleration command. Edit it to change the observations, the action mapping or checkpoint loading.

Plant: predict motion from low-level commands

Each 10 ms tick, the plant turns a four-value action into throttle and body rates. It delays and rate-limits that command, then runs five substeps of body-rate response, motor lag, drag and rigid-body motion. For example, with the default rate scale, action [0, 0.5, 0, 0] asks for throttle 0.475 and a 2.0 rad/s roll rate.

Action parser, plant state and physics update functions

Convert the deployed action to throttle and rates

parse_action(action, rate_scale=DEPLOY_RATE_SCALE) → (throttle_norm, br_ref)

The mapping of our deployed gate policies and rl_infer, our onboard program that runs them. It clamps the (N, 4) action, N = B, to [−1, 1]. Then throttle_norm = 0.15 + (a0 + 1)/2 · 0.65 (N, 1) and br_ref = a[1:4] · rate_scale in rad/s (N, 3). Tests compare it with JAX's gate_traversal_charpi._parse_action on raw actions.

Store the plant’s internal state

PlantState(br_state, thrust_state, prev_br_ref, cmd_buf, dr)

A NamedTuple mirroring JAX's CharpiState, minus the PRNG key and step counter; DR scales come from torch's RNG (sample_dr(num_envs, band)).

  • br_state (N, 3, 2): body rate and its derivative.
  • thrust_state (N, 1): motor-lagged total thrust, in newtons.
  • prev_br_ref (N, 3): last limited command.
  • cmd_buf (N, 2, 4): delay FIFO, newest first.
  • dr (N, 8): DR scales.

Advance one control tick

forward_full_step(pos, quat, lin_vel, state, throttle_norm, br_ref, br_fit, v_wind=None, acc_ext=None)

One CTRL_DT, in charpi's order:

  1. Push the command into the FIFO; take the one from two ticks ago.
  2. slew_limit_cmd.
  3. Target thrust: throttle_norm_to_thrust times the DR thrust scale.
  4. saturate_br_ref: per-axis ceiling, then all axes scaled by min(1, 1.1 / Σ(|bri| / 6)). Full rate on all axes, [4.0, 2.5, 3.0] rad/s, gives Σ = 9.5/6 ≈ 1.58, so every axis is multiplied by 1.1/1.58 ≈ 0.69.
  5. Five substeps.

Returns position, quaternion, velocity, body rate, the new state and the last substep's world acceleration.

  • approx_substep: per-axis second-order rate response ω̈ = K ωn² ωref − 2ζωn ω̇ − ωn² ω, with DR on ωn, ζ and τ. ω̇ is clamped to SLEW_CEIL. Explicit Euler uses the old ω̇, as in JAX; thrust has a first-order lag.
  • rigid_body_step: thrust times the inflow factor clamp(1 − |vbody,z|/35, 0, 1), lateral drag −4 ωeq ROTOR_DRAG_CONST · vbody,xy, quaternion integration and renormalisation. Two extensions are None in charpi_physics: v_wind (drag and inflow act on the airspeed) and acc_ext, an added world acceleration. That is DiffPhysDrone's dg, a random external-acceleration disturbance like a small gravity error.

Controller: turn acceleration into thrust and rotation

A PX4-style attitude controller picks a thrust direction and body rates that follow the requested acceleration. It caps tilt at 60°. A vertical-hold thrust floor adds thrust to hold height while the drone is still tilting.

feasible_accel clamps only the surrogate's command to what the nominal charpi plant can fly level; the plant gets raw u.

Attitude law, thrust formula, feasible acceleration and tick functions

Choose thrust and body-rate commands

ctbr_controller(u, heading, q, cfg=ControllerConfig()) → action (N, 4)

PX4's tilt-prioritised attitude controller (AttitudeControl::update + bodyzToAttitude) aligns the thrust axis first, then corrects yaw. Here it uses ENU/FLU axes and [x, y, z, w] quaternions (frames and units).

  1. Specific force f = u + g, the acceleration the rotors must supply, with fz ≥ 0.1 g.
  2. Scale fxy to keep the tilt within max_tilt_deg (60°).
  3. Desired attitude from body z = f/|f| and the heading; body rates from attitude_rates.
  4. Collective thrust T = m · max(flim · zbody, fz / max(zbody,z, 0.3)) (m: mass), through the inverse nominal thrust curve. The controller does not know the DR thrust scale.
  5. a0 = 2(η − 0.15)/0.65 − 1, a[1:4] = clamp(rates / rate_scale, −1, 1).

Why the max: the projection alone sank 0.1–0.9 m per manoeuvre while the attitude loop (about 0.3–0.45 s) caught up, and PX4's m|f| climbs as much. The vertical-hold floor keeps the height. ControllerConfig(att_gain, yaw_weight, max_tilt_deg, rate_scale) is frozen and rejects max_tilt_deg outside (0, 90).

Compute rates from attitude error

attitude_rates(q, qd, att_gain, yaw_weight)

PX4 AttitudeControl::update: the shortest-arc rotation that aligns the thrust axis (quat_from_two_vectors), then yaw blended in with yaw_weight; the yaw gain is divided by yaw_weight to compensate. Rates = 2 · qe,xyz · gain.

Limit the surrogate to feasible acceleration

feasible_accel(u, cfg) → u′

The part of u the controller and nominal plant can deliver in level flight. fz stays between the throttle floor (8.1 m/s²) and ceiling (30.9 m/s²). So uz lies in [−1.70, +21.1] m/s², and the same tilt limit applies. A request of uz = −5 m/s² becomes −1.70 m/s². Inside that set it is the identity, so it is differentiable and passes zero gradient to what the plant ignores. Only the surrogate sees it.

Run the controller and plant once

charpi_tick(p, v, q, st, u, heading, ctrl, br_fit, v_wind, acc_ext)

One 100 Hz tick: ctbr_controller on the current state, parse_action, forward_full_step. Returns p, v, q, st, acc, action. _charpi_ticks_flat(n, …), the eager path, loops it n times.

CharpiDynamics: connect the plant to the rollout

CharpiDynamics replaces env.run in the rollout. Its methods are reset, step, config and from_config. Each step runs the controller and plant, then writes their state into env.p/v/a/R with the surrogate's gradients. The --charpi_* flags configure it. config saves the settings in the checkpoint, so evaluation rebuilds the same plant.

Reset order. Call dyn.reset() after env.reset() and any episode override (evaluation's configure_env). It takes q from env.R and starts the plant in trim for env.act. It draws DR scales (band off when randomize is false) and sets the surrogate lag and drag.

Ticks per policy step. A 15 Hz policy step lasts 66.7 ms, not a whole number of 10 ms ticks. So step carries the remainder and runs 6–7 ticks per step. For example, round(6.67) = 7, round(13.33) − 7 = 6 and round(20) − 13 = 7 give 7, 6, 7, … ticks. With training's dt jitter a step runs 3–10 ticks; more than 8 needs two compiled calls.

Compilation: reduce GPU launch overhead

Compiling the tick loop cuts a 150-step rollout plus backward from 3.6 s in eager mode to 0.105 s. This microbenchmark ran on the RTX 5080 at B = 64; plain env.run (the point mass) took 0.015 s. Eager mode is slow here because the 100 Hz loop is a long chain of small GPU operations, each with launch overhead. With --charpi_compile (CUDA only), a step's ticks run as replays of a CUDA graph: GPU work recorded once and replayed with one launch.

The compiler is torch.compile: its dynamo stage traces the Python code, and Inductor generates and caches GPU kernels. The first iteration compiles for about a minute, or seconds once Inductor's on-disk cache is warm. The first 25 iterations of the toa_cbf_charpi run averaged 3.2 s per iteration. After that, inside training, the compiled tick loop alone costs about 0.09 s per iteration, small next to the TOA field build.

CUDA graph chunks, loose tensors and cached constants

Compile path

With compile=True (CUDA only), the constructor wraps the tick loop in torch.compile(_charpi_ticks_masked, dynamic=False, mode="reduce-overhead"), i.e. CUDA graphs, and step calls that instead of _charpi_ticks_flat.

  • One masked chunk. Each call runs TICK_CHUNK = 8 ticks; ticks with index ≥ n leave the state unchanged (torch.where), and n arrives as a 0-d tensor from a prebuilt list. So every tick count (ticks per policy step) shares one graph and one compile. Several ticks per graph also keep replays few. A replay overwrites its previous outputs, so step clones them after each call and marks a new step before it (torch.compiler.cudagraph_mark_step_begin()).
  • Loose tensors. The plant state goes in and out as separate tensors, not a PlantState: torch 2.11's dynamo fails on a NamedTuple that a compiled call returned and gets back.
  • _vec bypasses its cache while compiling. _vec caches small constant tensors per device to avoid host-to-device copies. A constant first cached inside the graph would become a graph output, overwritten by later replays. This crashed on the GPU; the fix builds graph constants fresh when torch.compiler.is_compiling().

11Evaluate a trained policy

evaluate.py flies a saved policy on repeatable scenes without changing its weights, and records each trial's outcome and speeds. Then compare.py compares the methods' success counts on the same trials.

By default (--dynamics auto) it flies the plant in the checkpoint's config["dynamics"]; a checkpoint without that entry counts as diffphys. Export (export_onnx.py) reads the same entry and has no --dynamics flag. In evaluation, --dynamics diffphys or charpi overrides the checkpoint. That allows a transfer test: flying a policy on a plant it did not train on.

A trial succeeds within 5 m of the goal and fails on a collision. Otherwise it times out after 3 × length / speed + 5 s: 26 s at 5 m/s on the 35 m route.

  1. Build the same scenes for every method

    Trial i gets the same scene for every method and requested speed, so comparisons are repeatable.

    Scene seeding and padding

    scenes.make_scenes(scenario, n_trials, spacing, seed)

    Each trial's numpy generator is seeded with (seed, scenario, trial). Unused slots are padded with primitives 10 km away.

  2. Pick the plant and the result name

    The default name is the variant, plus _charpi if trained on charpi, plus _on_<plant> if flown on another plant.

    Saved charpi settings and result names

    For charpi, evaluation rebuilds the plant from the checkpoint's saved settings with dyn = CharpiDynamics.from_config(env, cfg.get("charpi"), compile=args.charpi_compile, br_fit=args.charpi_br_fit). A diffphys checkpoint has no charpi entry and gets the defaults.

    Because the name records both plants, charpi runs no longer overwrite results/toa_cbf_*.json. The names in use:

    • toa_cbf: the paper's policy, trained on the point mass.
    • toa_cbf_charpi: trained on charpi. A config and run name whose --variant is toa_cbf; --variant takes only distance, toa or toa_cbf.
    • toa_cbf_on_charpi: the paper's policy flown on charpi. Only a result name.

  3. Set the starting conditions

    configure_env swaps the random episode for the fixed scene, start, goal and requested speed. With charpi, dyn.reset() follows (reset order).

    What configure_env sets

    configure_env(env, ops, scene, start, goal, speed, cfg, args), then dyn.reset(…)

    It runs after a normal env.reset(), also sets the margin, and faces the drone at the goal. Without --randomize_dynamics it sets nominal drag, delays and thrust (e.g. pitch_ctl_delay = 12 s⁻¹) and the checkpoint's camera. For charpi, dyn.reset(randomize=args.randomize_dynamics) then sets up the nominal plant (DR band off); the flag makes it sample the checkpoint's band instead. This reset also replaces DiffPhysDrone's lag and drag with the surrogate values in the table.

  4. Fly until success, collision or timeout

    The policy runs at 15 Hz with optional stereo-depth noise (--depth_noise stereo by default; none turns it off). Each policy step checks ten swept positions for collisions. Finished trials are frozen in the statistics while the batch flies on.

    Flight loop

    fly(env, model, cfg, scene, goal, speed, args, gen, dyn=None)

    This is the training loop without gradients, with dt fixed at 1/15 s. When dyn is given, dyn.step replaces env.run. Before each step, a scene_sdf value below the collision radius (--drone_radius, 0.15 m) at any of the 10 swept sub-positions ends the trial as a collision.

  5. Save per-trial results

    One JSON per run holds each trial's outcome and metrics, plus the plant flown.

    JSON keys
    • speeds[v]: per-trial lists (outcome, success, time, path_len, mean_speed, max_speed, min_clearance) and SR, Vel, Vel_success, n_collision, n_timeout.
    • trajectories[v] and scenes: the first --n_traj trials, for plots.
    • Top-level dynamics and charpi (dyn.config() or null): the plant flown.

  6. Compare success counts

    compare.py runs a Fisher exact test of the --ours method against each other method. --pool merges all settings.

    Test details and the charpi table

    It sums successes per method, speed and setting, then runs a two-sided scipy.stats.fisher_exact. P-values are unadjusted. scripts/experiments/eval_all.sh also evaluates toa_cbf_charpi. When both checkpoints exist, it writes results/table_charpi.md: toa_cbf_on_charpi vs toa_cbf_charpi in the 3 m forest.

The GPU parity test first asserts that quadsim_cuda is the real extension, then renders all primitives and each family alone. In each render, at most 8 of 98,304 pixels (32 scenes × 48 × 64) may differ by more than 1e-3 relative (0.1 %). Nearest points must agree within 1e-4 m (0.1 mm).

Why renderer parity counts differing pixels

Rays that graze the ground hit about 1e5 m (100 km) away and differ by float32 round-off. The old absolute 1e-3 m tolerance failed on them when the test first ran on a GPU. The count still catches a broken family: 0–2 pixels differ on the RTX 5080, while dropping one family changes 30–200.

Each file holds the inputs, parsed commands, every per-tick state and the JAX constant tables:

13Change or extend the code

Losses go in the training score (train.compute_losses), TOA solvers in the TOA field (toanav/toa.py), scenes in evaluation (scenes.py), and a new plant behind the --dynamics interface.

Add a loss term

Compute it in train.compute_losses from the rollout tensors. Add a --coef_… flag in get_args and the weight to the coef dictionary. Training then sums it, logs it as loss_<name> and back-propagates it:

# example: penalise altitude changes
L["alt"] = roll["v"][..., 2].pow(2).mean()
coef["alt"] = args.coef_alt

Try another TOA solver

Add a mode to propagate that returns (B, 1, Nx, Ny, Nz), with ∞ where unreachable. Then add it to three places:

  • a BFS comparison like tests/test_toa.py::test_safe_jfa_matches_bfs_without_leaks, which loops over metrics with jfa_safe fixed;
  • viz_toa.VARIANTS, which shows its error;
  • the --toa_mode choices, which select it for training.

Add an evaluation scenario

Write a generator in scenes.py that fills the four primitive lists per trial and returns _finish(trials, length, altitude, device). Register it in make_scenes and in the --scenario choices of evaluate.py.

Change the camera or the vehicle

Camera: set --fov_x_half_tan and --cam_angle at training; the checkpoint keeps them. The network's first layers fix the image size at 64 × 48.

The charpi plant is configured by --charpi_* flags, not code, e.g. --charpi_br_fit sitl and --charpi_dr_band real. They are saved in the checkpoint's config["charpi"]; CharpiDynamics lists them all.

Add another vehicle model

Copy the charpi pattern and keep its interface and straight-through merge. The new plant supplies the forward values (the flight); DiffPhysDrone's point mass supplies the gradients used in training.

  1. Port the plant

    A module like toanav/charpi.py: the plant, a controller from the acceleration command u to that vehicle's deployed action, and a class with reset, step, config and from_config. Its step sets env.p/v/a/R as CharpiDynamics.step does.

  2. Record a reference

    Run the original implementation on random actions, as scripts/charpi/charpi_reference.py does. Store the trajectories and constant tables in tests/data/; replay them in a test within a tight tolerance.

  3. Re-fit the surrogate

    Adapt scripts/charpi/fit_charpi_surrogate.py to the new closed loop. Use its best lag as the surrogate's pitch_ctl_delay (charpi uses SURROGATE_LAG = 5.0 s⁻¹) and the vehicle's hover drag as drag_2.

  4. Wire it in

    Add a --dynamics choice in train.py (get_args, make_dynamics) and evaluate.py, and a config in configs/. If the controller runs on board, add a "low_level" spec in export_onnx.py.

To change DiffPhysDrone's point mass itself, edit its CUDA kernel and quadsim_torch.run_forward/run_backward. Then run scripts/setup/check_install.py on the GPU; it compares every op of the two.
